# SoulLog — What Is Not Built, Simulated, or Deferred

This document exists so nothing important is silently missing. Every item
here was found during real development and testing, not guessed at
afterward. Status categories follow the spec's own classification
(§120.3): **COMPLETE**, **LOCAL IMPLEMENTATION**, **SIMULATED**,
**PARTIAL**, **ARCHITECTURE READY**, **DEFERRED**, **PRODUCTION REQUIRED**.

The previous version of this file listed six entire subsystems with
"polished UI, zero backend". Those are built. What follows is the current
honest account — shorter than before, and deliberately not empty, because
a few things genuinely remain and a few were decided against.

## Deliberately not built

These are decisions, not gaps. Each one could be built; each was judged
wrong to build, and the reasoning is here so the decision can be revisited
rather than rediscovered.

### Sleep & Mood and Weather Impact insights
**Status: PLANNED, NOT BUILT.** These two insight categories need data
SoulLog does not collect — sleep logs, and location or weather. The
original objection was that a wellness product should not quietly start
recording more about you than it said it would, and that objection still
holds; what has changed is the answer to it. Both become opt-in: the app
asks for location permission, the user grants it or doesn't, and the
insights appear only for those who did. Someone who leaves location off
loses these two insights and nothing else.

Worth noting for whoever builds it: a weather insight needs a location
*history*, not a current reading, since it correlates past moods with
past conditions. That means storing a coarse location per check-in —
city-level is enough, and city-level is the right resolution to store.

The other two of the four originally-fabricated categories (Weekend
Reflection Depth, Stress Response Evolution) turned out to be computable
from real data and are already implemented.

### "Mentoring sessions"
**Status: NOT BUILT.** Another person's profile used to show a
"Mentoring Sessions" count. There is no mentoring flow yet, so there is
nothing to count; the tile is gone rather than showing a zero that
implies the feature exists. When the mentor flow is built, this comes
back as a real number.

### Voice and video calling
**Status: NOT BUILT.** The Whispers header has phone and video icons.
They are drawn dimmed and inert rather than wired to anything. Real
calling means WebRTC, signalling, TURN servers and a mobile permissions
story — a subsystem of its own, not a button.

### Payments and subscriptions
**Status: OUT OF SCOPE (spec §99).** Unchanged from the previous version.
The "Billing" row in the account menu has been removed, because a menu
item leading to a billing screen advertises something that does not exist.

### Full groups / circles
**Status: DEFERRED.** `community.Topic` is a followable label, not a group
with membership roles, moderation and per-group privacy. Building that
machinery before anyone has decided what a SoulLog group *is* would be
building the wrong thing carefully.

## Partially built

### Journal list pagination
**Status: COMPLETE.** `GET /api/v1/journal/` returns
`{entries, total, offset, limit, hasMore}`, and searching, mood filtering
and sorting all happen in SQL. Both halves changed together, and two
things were fixed on the way that the old shape had been hiding: the
screen used to filter the array it was holding, so once that array became
one page "search" would have quietly meant "search the most recent
twenty"; and the sort compared `entry.date` and `entry.time`, fields this
API has never sent, so choosing newest/oldest/mood did nothing at all.

### Streak timezone
**Status: PARTIAL.** Unchanged and still honest: "calendar day" in the
streak calculation is computed in the server's timezone, not each user's.
The `User` model has no timezone field. A user near a day boundary can see
their streak flip a few hours off from their local midnight. Fixing it
properly means adding a user timezone preference and using it in
`DashboardStatsView`.

### Comment and message editing
**Status: COMPLETE.** All four places you can write a short piece of text
— journal comments, Sanctuary comments, library comments and messages —
can now be corrected, under one set of rules in `backend/core/editing.py`
so that "edit" means the same thing everywhere:

* Only the author. Not the owner of the post, not staff. A post owner can
  still *remove* an unwanted comment; rewriting someone else's words under
  their name is not a power this app should have.
* Visibly. `edited_at` is set and the UI shows "(edited)". A silent edit
  lets someone change what they said after it was replied to, which turns
  a conversation into an argument about what was actually written.
* Deleted stays deleted, and a message with only an attachment has no text
  to correct, so editing it is refused rather than turning it into a text
  message.
* Seven days. Long enough that nobody hits it fixing a typo, short enough
  that an old comment can't be repurposed after the thread has settled.

An edited message is pushed down the conversation socket, so the other
side sees the correction rather than the version they were replying to.

### Suggestion dismissal
**Status: PARTIAL.** "Remove" on a connection suggestion hides the card
for the current session only. There is no "not interested" record on the
server, so the suggestion returns on the next load. The alternative —
storing a dismissal — is a small model and was left out rather than
half-done; the current behaviour is at least not pretending to remember.

## Local development vs. production infrastructure

### Media & Storage
**Status: ARCHITECTURE READY, and now actually used.** Uploads exist
throughout: journal photos and voice notes, Sanctuary media, message
attachments, library media and thumbnails, avatars and covers. All of
them go through `core/uploads.py`, which validates type by content rather
than by the client's claim, enforces size limits server-side, and stores
files under random names partitioned by owner.

Storage is Django's configured default, so `USE_S3=True` plus bucket
credentials moves every upload to S3-compatible object storage with no
code change. Objects are private and URLs signed by default, because
journal media is personal data. **Production work:** create the bucket,
set the credentials, decide a retention policy.

### Email
**Status: LOCAL IMPLEMENTATION.** Password reset uses Django's console
backend by default, printing to the server log. Setting `EMAIL_HOST`
switches to real SMTP automatically. **Production work:** a provider,
domain verification, SPF/DKIM/DMARC.

### Background jobs
**Status: DEFERRED.** Nothing runs asynchronously. Insights are computed
per request, which is fast at current data volumes and always current.
The extension point is documented in `insights/engine.py`. **Production
work, if needed:** a worker (Celery or similar) for insight
precomputation and email sending.

### Real-time
**Status: COMPLETE.** Django Channels over ASGI. The channel layer is
in-memory when `REDIS_URL` is unset — so local development needs no extra
infrastructure — and Redis when it is set, which is **required** as soon
as the backend runs more than one worker process. Consumers know nothing
about which is in use.

### Monitoring / error tracking
**Status: ARCHITECTURE READY.** A Sentry hook is wired and entirely
opt-in: with no `SENTRY_DSN` nothing is imported and nothing is sent.
`send_default_pii` is off — journal entries are the most private data in
this product and must not leave in a stack trace. `/healthz` checks the
database and returns 503 when it is unreachable. **Production work:**
provide a DSN, and add uptime/latency monitoring.

### Deployment
**Status: ARCHITECTURE READY.** Dockerfiles for both halves,
`docker-compose.yml` for the whole stack (Postgres, Redis, backend,
frontend), Gunicorn with Uvicorn workers for ASGI, WhiteNoise for static
files, and GitHub Actions running the test suite against real Postgres
plus `manage.py check --deploy`. Security headers, HSTS and cookie flags
switch on automatically when `DEBUG=False`, and the app refuses to start
with `DEBUG=False` and the default `SECRET_KEY`.

**Production work that remains and cannot be done from here:** choosing a
host, TLS certificates, a real domain, database backups and restore
testing, and running migrations as a release step rather than on worker
startup.

### Mobile (Capacitor)
**Status: BUILDABLE; DEVICE TESTING STILL OUTSTANDING.** See
`mobile.md` for the full account. In short:

The native projects exist and are committed, the microphone permission is
declared on both platforms (Android `RECORD_AUDIO`, iOS
`NSMicrophoneUsageDescription`) so voice entries can actually ask for it,
and CI assembles a debug APK on every change — the mobile target was the
one thing nothing ever checked.

That is also how the worst defect here was found. `capacitor.config.ts`
set `server.url` to a hardcoded LAN address unconditionally, so every
build except the one made on that machine would have loaded a web server
on somebody's home network, found nothing, and shown a white screen. Live
reload is opt-in now (`CAP_SERVER_URL`), and CI fails if a `server` block
ever reaches a built config again.

What remains is the part CI cannot do: installing it on a phone and using
it. `mobile.md` lists the seven checks that need a real device — launch,
session persistence across a force-quit, the microphone prompt,
attachments, live messages over mobile data, socket reconnection after
sleep, and airplane-mode recovery.

## Demo data

**Status: COMPLETE.** `manage.py seed_demo` creates six demo accounts with
journal entries, mood check-ins, connections, posts, comments, reactions,
library items and conversations — all flagged `is_demo=True`, all created
through the same models and signals real registration uses.
`manage.py clear_demo` removes exactly those rows and nothing else.
`manage.py audit_demo_data` proves it: it reports demo rows by model,
finds content owned by a demo account that is missing its flag (which
`clear_demo` would otherwise leave behind), checks denormalised counters
against the rows they summarise, and exits non-zero on any problem so it
can gate a deploy.

One deliberate omission: seeded library items carry no media file. A
seeded library that appeared to contain video would be exactly the kind of
plausible-looking fiction this document exists to prevent. The cards
render; there is nothing to play, and the UI says so.

## Frontend type safety

**Status: COMPLETE**, and recorded here because it fixed two real bugs
rather than merely tidying the code.

The UI was written with `any` as its house style — screens took
`({ theme, darkMode }: any)` and passed loosely-shaped objects around;
there were about 300 of them. That is not a style question. Two live bugs
were hiding behind it, and both had been there as long as the screens
they were in:

* The Journal screen sorted on `entry.date` and `entry.time`, fields this
  API has never sent, so every comparison ran against `undefined` and the
  sort control did nothing at all.
* The app-wide theme object defined six keys while screens read
  seventeen. The other eleven — `cardBg`, `gradient`, `mutedText` and the
  rest — came back `undefined`, so those styles were silently dropped.

`any` did not cause either bug; it made both impossible to find. The
payload shapes now live in `frontend/src/types.ts` and the palette in
`frontend/src/theme.ts` (one definition, replacing six drifting copies).
`@typescript-eslint/no-explicit-any` is an error and `npm run lint` runs
with `--max-warnings 0`, so the next one can't get in. Where a shape is
genuinely unknown — a socket frame, a DRF error body — the code uses
`unknown` and narrows it, which is the honest version of the same
admission.

## Summary

**Real and tested:** authentication, journaling (including photo and voice
attachments, all four share settings, pagination with server-side search
and sort, and hearts on shared entries), mood check-ins, a six-analyzer
Insight Engine, dashboard stats, settings and account management,
connections and blocking, notifications, Whispers with live delivery and
presence, editing of comments and messages, the Sanctuary feed, the
content library, community discovery, achievements, opt-in reciprocal
profile views, and all three profile screens. 199 automated tests cover
it, including real WebSocket tests, alongside browser tests and an
Android build in CI.

**Not real:** voice and video calling (drawn, inert, labelled), payments,
and the items under "Deliberately not built" above.

**Still to do before real users:** per-user timezones, the device checks
in `mobile.md`, and the deployment work listed under Deployment.
